Amazon EC2 : it lets us rent a server from AWS in minutes. We can choose how much CPU, how much memory, and how much storage we need. We have full flexibility to start it, use it, stop it, and delete it.

On-Demand Instance : No commitment. Pay per second / hour. 
We pay for compute only for the time our instance is running, with no upfront payment and no long-term commitment. 
- testing with wide varieties of configuration, Dev/QA
- Short term or unpredictable workloads.

Cons: 
- Most expensive option per hour.
- If we are running 24/7 per month, it's costly. 

----

RIs : Reserved Instances : Commitment for 1 year or 3 years, and we get a significant discount compared to on demand, up to 72%. 

We have two types of RIs. 
- Standard RI : Biggest discount but we cannot change instance family. (Can change AZ or size with in the family)
- Convertible RI :  Smaller Discount. Can be exchanged for another convertible reserved instance with different attributes, like family, OS, and tenancy. 

3 pricing Options:
1. All Upfront : pay everything at the start. highest discount.
2. Partial upfront : pay some amount now. Pay the rest of the amount based on the usage with a discounted hourly rate. 
3. No Upfront : pay on an hourly basis. Cost is almost similar to on-demand but capacity will be reserved for the committed duration. 

AWS Marketplace : You can register as seller, Sell your reserved capacity. 

---

Spot Instances : No Commitment.. Discount upto 90%.
- Instances can be interrupted. 

AWS always has unused server capacity. Spot instances let us use the spare capacity at a huge discount. 
When AWS needs that capacity back, it can stop or terminate our instance with just 2 minutes' warning. 

This is a good option for batch jobs, data processing, video rendering, big data, or ML training that requires high configuration at low cost. 

- We can use pricing history to quote our price while purchasing spot instances.

---

Savings Plan : This is a modern replacement or improvement for RIs. AWS introduces this to reduce the reserved instance complexity. 

We are committing with AWS on hourly pricing. You give a commitment to AWS that you spend a fixed amount per hour on compute. AWS gives a good amount of discount. 

	- Compute savings plan : we can use this with multiple services like EC2, Lambda, and Fargate...
	- EC2 Instance Savings plan : we can use this with only EC2 specific to a particular region.. 
	- Sagemaker savings plan : AI/ML Workload
	- Database Savings plan : Database realted workload i.e; RDS, Elasticache..

Snapshot : a snapshot is nothing but a backup copy of an EBS volume. It works with a point-in-time copy mechanism. 

- Point in time means if you create a backup copy at 9:30, whatever data we have in the volume at 9:30, only that data will be backed up. 

- Can we see all the files we have in a snapshot? 
Answer: No. Attached to an EC2 instance by creating a volume from a snapshot, then only you can view the data. 

- AWS uses an incremental backup mechanism in the backend. We just need the most recent backup copy to restore data. 

- If we have a snapshot with "default encryption", WE CANNOT share it with another AWS account as they cannot decrypt it. 

- We can even make a snapshot public but remember we never, ever share our snapshots publicly as it contains a lot of sensitive corporate information. 

Interviewer: you have an unencrypted volume. You are asked to enable encryption for that particular volume. How can you do it? 
Ans: we don't have a direct option to modify a volume and enable encryption. We have to use a workaround solution:
1. Pick unencrypted volume and create a snapshot.
2. From the snapshot create a new volume.
3. While creating a new volume enable encryption.
4. Detach the old volume and replace it with the new encrypted volume at the instance level.

SLAs : Service Level Agreement : 

RTO : recovery time objective 
Question: how long can we afford to be offline?
Simple Meaning: downtime limit 
Example: if our RTO is 2 hours, our system should be-back "up and running" within 2 hours of a crash to avoid business losses. 

RPO : recovery point objective 
Question: how much data can we offered? 
Simple Meaning : data loss limit 
Example: if our RPO is set to 2 hours, we must have backup configured for every 2 hours or less than 2 hours. 


Lifecycle Manager / DLM - Data Lifecycle Manager : helps to automate the snapshot creation process based on intervals we configure.


DLM (Data Lifecycle Manager) uses the resource allocation tags to filter the resources at the instance level or EBS volume level. 

- We can filter using instance-level tags. We even have an option to exclude specific volumes.
- We can filter using EBS tags as well.


Question: Can you explain your EC2 instance backup strategy currently being followed in your project? 

- Filtering the resources (Tags: key & Values)
- Frequency
	- Production : 3 hrs
	- Non-Production: 12 hrs
Retention Period : 
	- Production: 7 Days... 
	- Non-Production: 3 Days..

=========

For taking backups of EC2 resources we are using the AWS default or AWS inbuilt service called DLM. Generally based on the environment or whatever resource we create, we are going to mandatorily allocate some tags to the resources, like project, OS, and client. In the same way we have a dedicated tag for backup strategy as well, where the key is equal to `backup` and the value varies from environment to environment.

For production we have set the backup frequency to 4 hours. For non-production the backup frequency is 12 hours. Also the retention varies from environment to environment. Mostly for production resources we are retaining snapshots for 7 days. For non-production we are retaining resources for 3 days.

EFS : Elastic File System 

- EFS works with a protocol called the NFS protocol. NFS - Network File System. 
- The NFS port number is 2049
- No pre-provisioning required. 
- We can store unlimited data. 
- Limitation: EFS supports only Linux operating systems. 
- EFS can be mounted to EC2 instances in multiple availability zones within the region. 
- We can mount it to hundreds to thousands of EC2 instances. 


We have to establish secured connectivity between EFS and EC2 instances. How can we achieve the utmost secure transfer between the servers? 


Secure pipeline mechanism between EC2 instance and EFS contains two steps:


Step 1. Create a security group for web servers who want to access EFS.

WEBServer-SG:
SSH : 0.0.0.0/0 / MyIP / Custom
HTTP : 0.0.0.0/0 / MyIP / Custom 

Step 2 : create a security group for the EFS service.

Problem : another EC2 instance running in the VPC can communicate or can access data we have inside EFS. 

Option 3 : pick EC2 instance private IP addresses and add to EFS security group. 
Problem : if we integrate with an auto-scaling group, instances will be deleted and new instances will come with new IP addresses. Manually we have to edit the EFS security group whenever any new instance creation happens. 

Option 4 : Open EFS for anywhere. It is a security risk, not a recommended option. 

Option 5 : attach the "default security group" for our EC2 instances and EFS as well.
By default the default security group is a loopback. It opens all traffic to itself.
